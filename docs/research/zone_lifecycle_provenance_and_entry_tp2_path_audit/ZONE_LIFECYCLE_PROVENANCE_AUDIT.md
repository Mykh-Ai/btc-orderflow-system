## Q1: significant-zone identity

It is a deterministic aggregate **for fixed input bytes and cutoff**, not a persisted economic object. Its number is output rank, so it is not guaranteed to survive later cutoffs. Boundaries, dominant type counts, and source membership can change as new windows enter or old ones leave; a cluster can encompass many price/time histories, and the suppression rule can remove or alter which aggregate is visible (`significant_market_zones.py:64-76,114-133,144-151,181-201,271-290`). Thus a formerly single cluster can separate when its input membership changes; the code has no persistence or invariant preventing it. This is a capability conclusion from the rebuild algorithm, not a claim that a particular split occurred in the 19 cases. On Aug 7, `EX_EN_1786107369` and `EX_EN_1786131443` both had `significant_zone_000001` at 64037.4–65689.6, but source count changed 180→181 and source type counts changed; their matched registry IDs changed `zone_000011`→`zone_000009` (matrix). The Sep trace shows significant `000003` retaining its number while its boundaries changed.

## Q2: matched registry identity

`_matched_registry` filters **all** registry rows with inclusive interval overlap, then minimizes absolute midpoint distance and breaks ties lexically by `zone_id` (`snapshot_v2.py:219-228`). It has no minimum overlap ratio, no side/status/type/timeframe condition and no comparison of source IDs. This includes `MERGED` or inactive rows if present. A significant aggregate can overlap several registry histories; 18 selected significant zones had 2–23 geometric candidate rows, and one case had no match. Five of 18 chosen registry rows had the trade-direction opposing side; 13 did not. Example: short `EX_EN_1779438963` selects a 76014.2–78648.0 significant aggregate, but matches buy-side `zone_000004` at 77290.24–77417.79, only 4.84% of aggregate width, among 18 overlapping registry rows. Lifecycle fields on that row describe its own structure, not the whole significant aggregate.

## Q3 and architectural answers

- Stable canonical identity between the selected significant zone and registry zone: **NO**. The two branches have different source families, independent rebuilt IDs, and no common lineage key; price intersection alone does not establish origin. `ZONE_IDENTITY_MATRIX.csv` classifies 18 `GEOMETRIC_MATCH_ONLY` and one `NO_MATCH`, none `PROVEN_SAME_OBJECT` or `PROBABLE_SAME_OBJECT`.
- **A. `NO_CURRENT_MAPPING_UNSAFE`** — attaching registry lifecycle to the selected significant zone as one object's lifecycle is not evidence-backed.
- **B. `PARTIAL`** — pre-cutoff minute events can be deterministically recomputed for a registry row visible at that cutoff from verified feed; persistent same-object history, objects filtered out at the latest close, full older-than-1440-minute lifecycle, approach/re-entry timestamps, and stable merge lineage are unavailable in the Snapshot call. See `ZONE_FIELD_SEMANTICS.md`.
- **C. `PARTIAL`** — raw pre-cutoff candidate intervals can be enumerated and ordered, but a provenance-safe, nonduplicated path cannot be produced from current IDs and links. See `ENTRY_TP2_PATH_FEASIBILITY.md`.
- **D.** `_recent_cleared` requires a same-trade-direction registry side, directional three-close acceptance timestamp, and price strictly beyond that row (`snapshot_v2.py:231-250`). Reconstructed 1440-minute registry rows yielded **zero** candidates satisfying all three in each of 19 cases (matrix column `recent_cleared_accepted_beyond_price_count`); this is the direct reason for null. It does **not** prove that no structure was cleared: the rebuilt registry omits older/invalidated zones and cannot track a historical structure after it disappears. The Sep trace demonstrates this limitation.

## Cutoff and leakage finding

The actual Snapshot V2 call path clips to `Timestamp <= fill.floor('min')` in `load_verified_feed` and rejects post-cutoff rows in `build_snapshot` (`snapshot_v2.py:83-98,340-348`), then scopes 1440-minute current and context windows (`:149-167,349-352`). For this path, the 19 reconstructed views are cutoff-safe. Lower-level builders `build_structure_levels`, `build_accumulation_zones`, `build_significant_market_zones`, `build_zone_registry`, `_update_lifecycle`, `_consumption_fields`, `_htf_lifecycle_metrics`, `_matched_registry`, and `_recent_cleared` do not themselves enforce a cutoff (`structure.py:39-65`; `accumulation_zones.py:24-59`; `significant_market_zones.py:41-76`; `zone_registry.py:147-164,547-581,609-710,925-982`; `snapshot_v2.py:219-262`). **FUTURE_LEAKAGE_RISK** if a caller supplies post-cutoff rows or objects built from them. `_zone_fact` checks named event timestamps against cutoff, but its bar interaction count would still read any future bars in `current` (`snapshot_v2.py:170-199`). No such leakage was found in the frozen Snapshot V2 build path.

## Width and interaction count

`_zone_fact` increments `interaction_count` for **every supplied minute bar** with `HiPrice >= lower` and `LowPrice <= upper` after that row's `first_seen_at`; adjacent minutes in one prolonged visit are counted separately (`snapshot_v2.py:170-195`). A wider interval intersects more bars, and an older interval has more eligible bars. Selected significant facts use up to 30-day `context`, whereas nested matched registry facts use only 1440-minute `current` (`:277-280`). The counts therefore have unequal observation windows even within one snapshot. In frozen `blind_run_v3/frozen_model_view_snapshots.jsonl`, `EX_EN_1779438963` records 29,806 interactions for its 76014.2–78648.0 aggregate versus 167 for matched 77290.23555–77417.78955 registry row. `EX_EN_1784376441` records 14,221 versus 0. These are bar-overlap totals, not counts of independent touches, and a zero may reflect the limited registry window. Conclusion: **`NOT_SEMANTICALLY_VALID_FOR_COMPARISON`** across differing widths, ages, or the significant/registry branches. No normalization formula was derived.
